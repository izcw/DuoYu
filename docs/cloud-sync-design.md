# 多鱼云同步方案

状态：第一版云同步 API 与扩展自动同步已实现并部署。本文保留设计原则；实际结构以 `server/sync/schema.sql` 为准，交付、限制和测试结果见 `cloud-sync-delivery.md`。

## 目标和边界

云端是登录账号的权威版本，本地 IndexedDB 是缓存、离线工作副本及未提交修改的可靠队列。正常联网时自动双向同步；离线时允许修改并提示待同步。无法在断网期间承诺所有设备实时一致，目标是联网后收敛、不静默丢失修改、不串账号。

拓扑：扩展 → HTTPS 同步业务 API → 独立 PostgreSQL 数据库 `duoyu_extensions`。账号中心仅负责身份认证，不保存收藏业务数据。扩展不直连 PostgreSQL，不携带数据库密码或宝塔密钥。建议独立 Go 服务，与现有 DuoYu ID 使用相同运维技术栈，但代码、数据库、运行账户和权限分离。

账号键使用已验证的 `(issuer, sub)`，不使用邮箱、昵称或前端传入的 user_id。同步 API 必须验证供本服务使用的 Access Token，不能拿 ID Token 当 API 授权。上线前确认 DuoYu ID 的访问令牌格式、audience 和项目绑定方式：JWT 严格验签并验证受众；若为 opaque token，由服务端使用独立保密客户端和 introspection，校验 active、client_id、scope、sub。不能只解码 JWT 或仅依赖 CORS。当前公共扩展客户端没有 introspection secret，这是服务端接入需要确认的协议项。

## 首次登录、切换账号与退出

1. 现有 `duoyu` 库保留为访客空间；登录数据迁到按账号隔离的库。不能在当前共享库上仅改一个 activeUser 字段。
2. 首次登录先获取云端一致性快照，在暂存库完整校验后原子切换显示；不直接清空现有库再下载。云端为空时显示空账号空间，提供显式“导入本机数据”，不自动把访客内容绑定给首次登录账号。
3. 后续登录先显示该账号缓存并拉取云端增量；缓存有未上传修改时，先拉取到影子副本再进行重基，不能覆盖待提交修改。下载失败保留缓存，标记离线。
4. 导入是带 operation_id 的幂等事务，旧数据 ID 建立映射；重复点击不能生成重复收藏。相同网址可能有不同标题、图标或所在文件夹，不能仅按 URL 自动去重。
5. 切换账号先停止请求，使用会话 generation 拒绝旧请求回写；未同步队列留在原账号库。退出清除凭证并返回访客空间，可选择清除此设备的账号缓存；不自动删除云端数据。

## 本地可靠写入与自动触发

IndexedDB 增加 syncMeta（设备 ID、cursor、schemaVersion）、outbox（operation_id、base_revision、patch、base_values、状态）、shadow（已确认的云端副本）及 conflicts。修改业务数据和写 outbox 必须处于同一个 Dexie 事务；不能依赖 Vue watch 或 liveQuery 事后生成日志，否则崩溃会漏同步。

所有写路径统一进入 repository 层，包括批量修改、拖动、文件夹合并、删除、导入和设置；设置从 localStorage 迁入可参与事务的设置表，UI 只作投影。拉取应用使用独立路径，不再次写 outbox。用 Web Locks 或 IndexedDB 租约确保多个新标签页只有一个同步调度者；数据库唯一 operation_id 提供第二层幂等。

修改后约 800ms 防抖上传，连续输入最多延迟 5 秒；拖拽仅在松手后提交，图标挤开涉及的所有位置一次成组提交。联网恢复、账号恢复、窗口聚焦时立即同步；活跃时每 30 秒拉取变化，可后续改为 SSE 失效通知。扩展休眠时不能保证严格的秒级定时，使用浏览器 alarms 做后备唤醒，需增加对应权限。关闭页面不依赖 unload 发网络请求，队列已经持久化。

超时使用指数退避和随机抖动；429 尊重 Retry-After；401 通过现有后台串行续期一次，失败保留队列并要求登录；403 停止本账号同步；409 进入重基/冲突流程；网络失败保留原 operation_id，不重新生成 ID。刷新令牌的请求结果不确定时仍按现有逻辑重新认证，不能套用业务写请求的幂等重试。

## 服务端提交协议

API 草案：GET /v1/sync/snapshot、GET /v1/sync/changes?after=cursor、POST /v1/sync/operations、GET /v1/sync/status、POST /v1/assets。所有响应携带 schemaVersion；cursor 和 bigint revision 用十进制字符串传给 JavaScript，避免超过安全整数。

每次写请求携带设备 ID、稳定 operation_id、请求摘要、实体 base_revision、字段 patch 及用于三方合并的基础值。服务端只认可认证结果中的账号。相同 operation_id + 相同摘要返回原回执；摘要不一致返回409。请求超时后原样重试，确保已提交请求不会重复新增。

数据库事务首先 SELECT sync_accounts ... FOR UPDATE，串行化同一账号提交，然后检查幂等回执、版本和业务约束。递增账号 head_revision，在同一事务内写全部实体、完整变更记录和幂等回执，提交后才返回成功。不同账号不互锁。不能拿全局 bigserial 自增当作提交顺序游标，否则后分配但先提交的事务会让客户端跳过尚未提交的数据。

单个 operation 可包含一批有关联的变更：拖动和挤开、移入文件夹、跨页、删除文件夹等必须全部成功或全部失败。变更分页不得截断一个 operation，同一修订号的全部变化放在一个 changes JSON 数组中；设置每批大小上限，例如200项/1MiB，过大拒绝并由业务拆为合法操作，而非服务端半提交。

下载采用快照一致性：分页快照基于固定 snapshot_revision 和短期快照任务，或小数据使用单次 REPEATABLE READ 返回；读取增量先固定 head 上限，返回该上限内已提交的完整操作。客户端在同一个 IndexedDB 事务写数据、shadow 及 cursor；崩溃后可重复应用，不能先前移 cursor。

## 冲突决策

| 场景                     | 处理                                                                                                                           |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| 两台设备改不同项目       | 各自提交，互不冲突                                                                                                             |
| 同一项目改不同字段       | 基于 shadow/base/current 三方合并；只合并当前云端仍等于 base 的字段                                                            |
| 同一字段两边都改且值不同 | 云端保持权威；本地版本和 base 保存到 conflicts，提示可恢复/另存，禁止静默覆盖便签                                              |
| 删除与编辑并发           | 云端删除保留 tombstone，拒绝旧版本修改；将本地修改留作冲突副本，显式恢复才建立新操作                                           |
| 文件夹和子项并发移动     | 位置字段 pageId/parent/order/gridX/gridY/width/height 是一个原子域，不能逐字段拼接；验证同账号、父项类型、无环、同页和网格界限 |
| 拖动挤开多个项目         | 整组比较版本，一项冲突就整组拒绝；拉取新布局后重算，不能先写一半位置                                                           |
| 不同设备网格尺寸         | 同步逻辑坐标；小屏只改变显示缩放或视图投影，不能把显示适配结果自动写回云端                                                     |

云端默认优先不等于每次无条件覆盖本地。多设备同时编辑必然可能冲突；通过版本、幂等、事务与冲突副本保证可解释和不丢数据。设备时钟只用于显示，不作为胜负判断依据。

## 删除、历史与运维

实体删除写 tombstone，同时写变更。建议保留变更与删除标记90天；设备 cursor 早于 min_retained_revision 返回410，触发重新快照，旧队列逐项重基且不得复活已删除数据。幂等回执保留期应覆盖允许重试的最长设备离线期；第一版建议不清理回执，仅保留紧凑操作摘要/结果。不要把回执和变更清理混为一谈。

每日加密数据库备份，设置保留期，定期演练恢复；PITR/WAL 归档与附件备份同步规划。快照替换或账号恢复必须生成新修订，通知设备全量重拉，不直接把 head 回退。备份用于灾难恢复，版本历史用于单条恢复，二者独立。

数据库仅监听本机/私网，不开放公网5432。创建独立库和独立业务角色；迁移角色拥有 schema，运行角色只获必要 DML，非超级用户、不可建库/建角色。每条业务查询都带 account_id，并建议加 RLS 双保险（事务内 SET LOCAL app.account_id，连接池不可残留；运行角色非表 owner 且无 BYPASSRLS）。管理接口不暴露给扩展。文件下载也验证归属，限额、文件类型、尺寸和哈希必须校验。

## 本项目落地顺序与验收

1. 独立数据库、迁移、同步 API 与 API 令牌验证；确认生产业务域名和反向代理。
2. repository 写入统一、账号库隔离、outbox/shadow、云端快照优先；完成库迁移备份后再开放自动同步。
3. 页面/收藏/文件夹/组件/Dock 增量同步，再加入工作区标签和附件。
4. UI 展示已同步、待上传、离线、冲突状态；失败不假装成功。

验收必须覆盖双设备同字段冲突、不同字段合并、删除并发编辑、离线多天重连、响应丢失重试、相同operation_id异参、提交中崩溃、拉取应用中崩溃、多标签页同时同步、账号切换中的迟到响应、过期cursor重建、文件夹循环及跨账号父项、原子布局与云端容量不足、附件孤儿回收、无权账号访问。验收数据使用专用测试账号，不碰真实收藏。
